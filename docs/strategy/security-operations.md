# 보안·개인정보·운영 준비 전략

상태: 출시를 위한 요구사항 초안. 현재 기능을 인증하거나 운영 준비 완료로 선언하지 않는다. CN-005에서 실제 자료 흐름과 환경을 조사하고, CN-037에서 독립 검토와 복구 훈련을 수행한다.

## 1. 운영할 제품과 사용자가 만든 프로그램을 구분

Cannon 편집기/엔진/패키지 서비스의 장애와, Cannon으로 만든 고객 서비스의 업무 오류는 별개의 책임이다. 자체 도구의 CI 성공을 고객 서비스의 SLA로 확장하지 않는다. 각 배포는 지원 범위, 담당자, 데이터 소유자, 외부 효과, 백업과 장애 연락 경로가 있어야 한다.

로컬 단일 사용자 개발이 기본이다. 팀 서비스가 추가되면 조직/프로젝트/사용자 권한과 데이터 격리를 별도로 시험한다. 현재 module import/export 검사는 설계 연결 규칙이지 개인정보 접근 제어가 아니다.

## 2. 위험별 요구사항

| 위험 | 필요한 통제/설계 | 확인 방법 | 작업 |
|---|---|---|---|
| 잘못된 현재 상태 표시 | 소스·입력·실행 설정·요청 버전 연결, 과거 근거 분리 | 편집 중 오래된 응답/재시작/버전 전환 시험 | CN-015~021 |
| 검토와 다른 내용 적용 | exact candidate와 현재 baseline 검사 | 다른 파일 수정·동시 편집·review 재사용 검사 | CN-016/017/024 |
| 정답 기준 은폐 | original acceptance를 후보와 별도로 보존 | 입력/기대값 수정·테스트 삭제 사례 | CN-011/016/023 |
| 원문·비밀·trace 외부 유출 | 전송 범위/대상/보존 정책 명시, 최소 문맥, opt-in | fake endpoint의 실제 payload와 표시 내용을 비교 | CN-025~027 |
| 미리보기의 실제 쓰기 | 실행 mode와 실제 효과 경계를 구분 | 테스트 대상 쓰기 횟수·영향 범위를 확인 | CN-028~031 |
| 자원 고갈·장시간 정지 | 입력·분석·trace·history·큐에 한도, 취소와 진행 상태 | 한도·부하·긴 세션·중단 시험 | CN-012/020/029/036 |
| 업데이트/저장 실패 | 설치 artifact와 데이터 호환성, journal·backup·복구 절차 | 모든 지원 환경의 중단/손상/디스크 부족 시험 | CN-017/031/034/037 |
| 공급망/운영 권한 혼합 | 최소 권한, 고정 의존성, 빌드와 배포 역할 구분 | workflow/의존성 검토, 출처·배포 artifact 검사 | CN-033/037/040 |

이 표는 일반적인 방어 요구사항이다. 적대적 코드를 안전하게 실행하는 sandbox나 모든 위협을 차단한 제품이 현재 존재한다는 뜻은 아니다. 실제 검사 범위와 잔여 위험을 별도로 기록한다.

## 3. AI 통합의 자료 정책

소스, 프로젝트 설정, 테스트 입력, 원래 기대값, 실행 trace, 파일 경로, 사용자 식별값을 자료 목록에 포함한다. 각 자료에 local-only/허용된 공유/민감 수준과 소유자를 지정한다. 비밀 탐지는 보조 장치이며 완전한 비밀 제거의 증거가 아니다.

실제 AI 연결을 켜기 전 공급자, 송신 대상 자료, 보존 여부, 이용 비용과 중단 방식을 사용자에게 보여준다. 기본 개발 흐름은 AI 없이도 계속된다. 새 provider를 추가해도 공통 검토/원래 사례 재검사를 건너뛰지 않는다. 서버/도구의 설명은 실제 권한 검사와 다르다. MCP 사양도 동의·자료 보호·도구 안전성을 구현 책임으로 다룬다.[S2]

기본 진단 로그에는 비밀과 업무 원문을 넣지 않는다. trace export는 포함된 자료를 보여주고 명시적으로 수행한다. debug bundle은 redaction 결과와 누락 범위를 알려야 한다. 텔레메트리는 최소 수집·해제·삭제·보존 기간을 정하고, 수집 미동의가 핵심 로컬 기능을 막지 않게 한다.

## 4. 빌드·의존성·릴리스 통제

외부 라이브러리/Action/toolchain의 버전·출처·라이선스를 추적한다. 업데이트는 별도 diff와 검사 근거를 남긴다. 사용 가능한 검증된 라이브러리를 두고 암호·프로토콜 처리를 직접 작성하는 것이 자동으로 더 안전하다고 가정하지 않는다.

GitHub Actions에는 작업별 최소 권한, 검토된 Action의 immutable pin, 빌드/배포 권한 구분을 적용하는 작업을 둔다. GitHub의 공식 secure-use 지침을 확인하고 실제 workflow에 맞게 검토한다.[S5] 이 계획 커밋 자체는 workflow 권한을 바꾸거나 배포를 활성화하지 않는다.

SBOM과 build provenance를 release artifact와 함께 관리한다. SLSA v1.2를 비교 틀로 사용하되, 체크리스트와 빌드 플랫폼의 실제 통제를 검증하기 전에는 특정 level을 달성했다고 쓰지 않는다.[S4] 릴리스 signing이나 attestation도 업무 규칙의 정답을 보증하지 않는다.

SSDF는 안전한 개발 과정과 취약점 대응을 빠뜨리지 않기 위한 참고 틀이다.[S3] 출시 전 보안 연락 경로, 영향 범위 판정, 패치 검증, 사용자 통지와 지원 버전을 정한다. 연락처를 만들지 않고 있는 것처럼 SECURITY 문서에 쓰지 않는다.

## 5. 관측과 SLO

기본 운영 지표는 실행/검토 성공·실패·취소, 응답 시간, 메모리/trace/큐 사용량, 저장 충돌, 복구 횟수, 실제 배포 version, adapter 오류다. high-cardinality 원문이나 사용자 비밀을 label로 넣지 않는다. OpenTelemetry의 trace 연결 개념은 사용할 수 있지만 제품의 의미적 실행 근거와는 다른 자료다.[S7]

local CLI에 서버 uptime SLA를 붙이지 않는다. team/service profile을 채택하면 성공한 유효 요청 비율, latency, 오류 예산과 측정 구간을 먼저 정의한다. 초안 예시 30일 99.9% 가용성이나 RPO 15분/RTO 4시간은 owner·운영 자원·복구 시험이 확정되기 전 고객 약속이 아니다. 이 숫자가 기본 운영 설정이라는 뜻도 아니다.

오류 예산이 소진되면 기능 추가보다 안정화·복구를 우선한다. 새로운 기능을 위해 오류 측정 분모나 제외 조건을 조용히 바꾸지 않는다. dashboard가 없으면 log만으로도 같은 기준을 재현할 수 있게 한다.

## 6. 장애 대응·복구 런북

출시 전 담당자를 지정하고 다음 runbook을 실제 테스트 환경에서 수행한다.

- 잘못된 릴리스: 배포 중단, 정확한 영향 버전 확인, 이전 artifact 복원, 데이터 호환성 확인, 회귀 재검사.
- 소스/metadata 손상: 현재 작업 보존, journal/backup 확인, 복구 또는 명시적 충돌, 원문 손실 여부 확인.
- 데이터 이행 실패: 영향 범위 고정, 백업 복원 또는 forward-fix, 이미 발생한 외부 효과 별도 조정.
- 자격증명 노출: 사용 중단·교체, 영향 범위와 로그 확인, 검토된 패치와 필요한 통지.
- 공급자 장애: 타임아웃/취소, 반복 호출·비용 제한, AI 없는 수동 흐름 유지. 업무 효과의 무조건 재시도 금지.

심각도·연락 대상·on-call 시간·초기 대응 목표는 운영 owner가 확정한다. 초안 문서만으로 24시간 대응을 약속하지 않는다. postmortem은 원인, 실제 손실/영향, 검사에서 놓친 이유, 재발 방지와 담당 task를 남긴다.

## 7. 출시를 막는 운영 미비

지원 타깃의 설치 실패, 복구 불가한 데이터 손실, 권한 경계 불명, 실제 공급자 송신 정책 미정, 책임자 없는 incident 대응, 라이선스 미정, 위협 모델의 차단 위험 미해소는 GA를 막는다. 사소한 문서 오류와 같은 예외 절차로 처리하지 않는다.

최종 QA는 [quality-release](quality-release.md)의 G5~G7에 연결한다. 시험하지 않은 통제는 `not-tested`, 없는 기능은 `not-implemented`, 의도적 scope 제외는 owner 이유가 있는 `not-applicable`로 구분한다. 참고 출처는 [sources](sources.md)에 있다.
